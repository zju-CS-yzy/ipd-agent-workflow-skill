## 发布阻断与验收要求

### R1（已修复）：重新验证要求未阻止旧通过结果继续满足 TR4

以下复现描述初次核对时的实现，修复后的行为见本节末尾。

位置：`ipdctl/requirements.py` 的 `assess` 分支与 `readiness()`，以及 `ipdctl/requirement_contract.py` 的 `VERIFICATION` 契约。

本次合成复现使用公开测试夹具和正式 `preview()` / `apply_plan()` 接口：

1. 登记 `ir-1@1 → sr-1@1 → ar-1@1`，冻结范围、完成分解声明和成果关联，三层各登记一项通过结果。
2. 追加 `ar-1@2` 并纳入本轮范围，只给新 AR 登记新结果。
3. 将该变更的**每个影响对象**都评估为 `reverify`，明确要求重新执行 IR/SR 验证。
4. 保留原来的 IR/SR 结果，调用 TR4 `readiness()`。

预期：IR/SR 的重新验证未完成，拒绝就绪。实际：返回空诊断 `[]`，仍视为就绪；随后调用 Gate 需求 `enforce()` 同样没有拒绝。该检查也是 Gate 受理使用的检查之一；这不是“自动取得批准”，但会使人工决定前的预检错误地放行。现有例行测试未覆盖此组合。

原因：评估只检查对象集合是否齐全以及是否存在 `defer`；`reverify` 与 `unaffected` 都能解除未知影响诊断。结果记录没有绑定本次变更/适用上下文，旧通过结果只要证据文件摘要不变便可继续使用。

验收：把 `reverify` 转成有版本和上下文的待验证义务，要求相关结果在该变更之后按当前输入产生；明确 `unaffected` 和历史复用的授权及适用性。覆盖“仅改 AR、父层需复测”“跨增量复用”“新结果仍引用旧上下文”“未重新执行”“有效复测解除阻断”等独立预期用例，旧基线结论保持不变。

修复：新结果由 Skill 生成 `context_sha256`，接受的评估带 `assessment_revision`；上下文包含直接规范/文档输入和适用重验轮次，排除结果追加与无关状态 revision，避免结果自我失效。当前需求、实例、关联成果和 Gate 的重验要求都会约束相应需求；再次评估开始新轮次，采用更后版本不能绕过较早的适用重验。`unaffected` 不自动使无关需求失效。历史复用须匹配原结果上下文，精确重放旧请求不产生新证明。旧无上下文记录只读保留，当前就绪检查报告未知，Dashboard 的当前覆盖不再将其计作通过。实际测试执行和所填观察仍由调用者提供，登记操作不替代测试。

### R2：增量上下文尚未进入全部阶段与完成事件

位置：`ipdctl/project.py` 的 `verify_project()` / `lifecycle_complete` 事件，以及现有 Runtime 事件契约。

需求操作事件带有增量字段，但常规阶段事件及 `lifecycle_complete` 仍沿用旧契约；完成事件只记录 `phase`、`state_revision` 等，未显式绑定增量。`begin` 会创建新一轮状态和 Runtime；旧轮历史保存在冻结快照中，因此不是已发现的历史丢失，但尚不满足规划中的“事件显式携带增量上下文”。

验收：在保留旧项目读取兼容性的前提下，为启用模型的阶段推进、验证和完成事件加入明确增量/基线上下文，同步 Schema、验证器和双语说明；完成第二轮到 B2，证明事件与证据不会串轮。

### R3：模板选包不能替代 QA 模板的评审/发布记录

位置：`ipdctl/requirement_contract.py` 的 `TEMPLATE_PACK`，`ipdctl/documents.py` 的 `load_pack()`，以及 `pin_templates` 操作。

现有 `pin_templates` 保留操作者和理由，解决的是项目选择哪个模板包；包契约没有模板评审/发布记录、评审对象摘要及发布版本的关联字段，也没有单独受理该记录的路径。不能据此宣称规划中的 QA 编写、评审、发布闭环已经完整实现。

验收：定义最小显式人类授权发布记录及其与包摘要/版本的关系，验证缺失、篡改、版本不匹配和历史解析。仍沿用当前显式授权声明边界，不提前要求 v0.6.1 的可信平台身份映射。

### R4（已修复）：需求表中的无效上层版本引用仍可通过结构检查

以下为空检查缺陷的历史复现；修复已接入文档 lint 和项目 Gate/Owner 就绪检查。

位置：`ipdctl/document_tables.py` 的 `lint_tables()`，`ipdctl/documents.py` 的 `lint()`，以及调用该检查的 `readiness()`。

本次读取公开示例 `zh-CN/SR-TR2.md` 及其受控实例元数据，确认原稿 lint 为 `[]`；仅在内存中把上层 `ir-01@1` 替换为不存在的 `missing-ir@999`，再次 lint，实际仍返回 `[]`。示例源文件没有被修改。

随后扩展至中文/英文的 SR-TR2 和 AR-TR3 共四份表，分别替换其上层 IR/SR 为 `missing-parent@999`，四个原稿与四个错误版本均返回空诊断。

当前检查核对需求 ID 列与实例清单，但没有对上层版本列执行存在性和主分解关系核对。项目级 `readiness()` 也未增加这一检查。教学示例另有专用复核器，不能据此宣称一般项目的引用完整性已得到同样保护。

验收：管理表中的受控引用与规范登记逐行核对，至少拒绝悬空父版本、错误层级、与规范父关系不一致及不符合本轮锁定上下文的父版本；保留合法共享单元格、历史精确版本和显式派生需求。两种语言分别覆盖正反例。这属于机器引用完整性，不是 v0.7 才处理的论证充分性或内容质量判断。
